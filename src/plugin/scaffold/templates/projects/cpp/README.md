# __OLL_PLUGIN_NAME__

This is a C++ onelastleaf plugin generated by `oll plugin new`. The sample
`echo` action returns its arguments in order, so you can begin with a working
request path instead of an empty project.

## Requirements

- A C++20 compiler
- CMake 3.24 or newer
- protobuf and gRPC development packages
- oll

## Build and test

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Use `build/` as the incremental build directory. Reusing it preserves CMake's
configuration and compiler outputs, and it is already ignored by Git.

## Local source development

Install directly from this workspace, then start or recycle the plugin:

```sh
oll plugin install . --source
oll plugin restart __OLL_PLUGIN_NAME__
oll plugin call __OLL_PLUGIN_NAME__ echo -- one two
```

After an edit, rebuild and test, then run `oll plugin update
__OLL_PLUGIN_NAME__`. oll's source recipe builds in this same `build/`
directory, so it can reuse your incremental work. An update publishes a new
generation but leaves a running process alone; restart the plugin to load it.

## Local release development

Install the compiled program into a clean package root and include the exact
runtime manifest:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF \
  -DCMAKE_INSTALL_PREFIX="$PWD/build/oll-release/package"
cmake --build build --target install --parallel
cp oll.toml build/oll-release/package/oll.toml
tar -czf build/__OLL_PLUGIN_NAME__-dev-x86_64-unknown-linux-gnu.tar.gz \
  -C build/oll-release/package .
```

Create `oll-release.json` in the project root:

```json
{
  "format_version": 1,
  "plugin_id": "__OLL_PLUGIN_ID__",
  "default_release": "dev",
  "releases": {
    "dev": {
      "packages": [{
        "target": "x86_64-unknown-linux-gnu",
        "path": "build/__OLL_PLUGIN_NAME__-dev-x86_64-unknown-linux-gnu.tar.gz",
        "archive": "tar.gz"
      }]
    }
  }
}
```

Choose the canonical target matching your machine, then exercise the package:

```sh
oll plugin install . --release dev
oll plugin restart __OLL_PLUGIN_NAME__
```

`build/` is also the recommended home for package staging, so neither normal
incremental outputs nor temporary release archives spill into the source tree.

## Development loop

For everyday work, edit, build, run CTest, update the source installation, and
restart. Before publishing, repeat the check through local release mode; that
catches missing shared libraries, install rules, and manifest mistakes. Do not
launch the binary directly because oll owns the plugin endpoint and lifecycle.

## Publish a release

Build an archive for every supported target. Upload each archive, replace its
local `path` with a remote `url`, and record the exact `size_bytes` and SHA-256
`sha256`. Commit both manifests, tag the release, and test the public route:

Linux packages use `tar.gz`; Darwin packages use `zip`. Keep each filename,
target, and `archive` value aligned.

```sh
oll plugin install <git-remote> --release <release-id>
oll plugin restart __OLL_PLUGIN_NAME__
```
