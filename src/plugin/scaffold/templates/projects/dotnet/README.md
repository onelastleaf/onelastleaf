# __OLL_PLUGIN_NAME__

This is a C#/.NET onelastleaf plugin generated by `oll plugin new`. The sample
`echo` action returns its arguments in order, which gives you a small working
endpoint to build on.

## Requirements

- .NET 10 SDK
- oll

## Build and test

```sh
dotnet build src/Plugin.csproj --configuration Release
dotnet test tests/Plugin.Tests.csproj
```

.NET keeps incremental build state in `src/bin/`, `src/obj/`, `tests/bin/`, and
`tests/obj/`. Leave those directories in place while developing; they are
already ignored by Git.

## Local source development

Install directly from this workspace, then start or recycle the plugin:

```sh
oll plugin install . --source
oll plugin restart __OLL_PLUGIN_NAME__
oll plugin call __OLL_PLUGIN_NAME__ echo -- one two
```

After an edit, run the tests and repeat `oll plugin update
__OLL_PLUGIN_NAME__`. The source recipe runs `dotnet publish` against this
workspace, so the normal incremental caches remain useful. Updating publishes
a new generation but does not replace a running process; run `oll plugin
restart __OLL_PLUGIN_NAME__` when you want to exercise the new build.

## Local release development

A release package contains the published application and the exact `oll.toml`
that oll should use at runtime. For a GNU/Linux x86-64 development package:

```sh
dotnet publish src/Plugin.csproj --configuration Release \
  --output build/oll-release/package
cp oll.toml build/oll-release/package/oll.toml
tar -czf build/__OLL_PLUGIN_NAME__-dev-x86_64-unknown-linux-gnu.tar.gz \
  -C build/oll-release/package .
```

Create `oll-release.json` in the project root:

```json
{
  "format_version": 1,
  "plugin_id": "__OLL_PLUGIN_ID__",
  "default_release": "dev",
  "releases": {
    "dev": {
      "packages": [{
        "target": "x86_64-unknown-linux-gnu",
        "path": "build/__OLL_PLUGIN_NAME__-dev-x86_64-unknown-linux-gnu.tar.gz",
        "archive": "tar.gz"
      }]
    }
  }
}
```

Use the canonical target for your machine, then install and run that package:

```sh
oll plugin install . --release dev
oll plugin restart __OLL_PLUGIN_NAME__
```

Keep `build/oll-release/` for repeated local packages if you want an isolated
staging area. The language's useful incremental state still lives in the usual
`bin/` and `obj/` directories.

## Development loop

Use source mode for day-to-day editing: change code, test, update, restart, and
call the action. Use local release mode before publishing to catch packaging
mistakes such as a missing DLL or a stale manifest. Do not launch the plugin
directly; oll supplies its private endpoint and manages the process.

## Publish a release

Build one archive for each supported target. Upload the archives, replace each
local `path` with a remote `url`, and add its exact `size_bytes` and SHA-256
`sha256`. Commit `oll.toml` and `oll-release.json`, tag the release, and verify
the same path users will take:

Linux packages use `tar.gz`; Darwin packages use `zip`. Keep each filename,
target, and `archive` value aligned.

```sh
oll plugin install <git-remote> --release <release-id>
oll plugin restart __OLL_PLUGIN_NAME__
```
