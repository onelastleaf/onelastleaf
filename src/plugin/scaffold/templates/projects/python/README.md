# __OLL_PLUGIN_NAME__

This is a Python onelastleaf plugin generated by `oll plugin new`. The sample
`echo` action returns its arguments in order and gives you a working SDK path
to extend.

## Requirements

- Python 3.11 or newer
- uv
- oll

## Build and test

Let uv create one development environment and keep reusing it:

```sh
uv sync --extra dev
uv run --extra dev pytest
```

`.venv/` and uv's shared download and wheel cache are the recommended
incremental environment state. Use `build/` for release staging; both project
directories are ignored by Git. Commit the generated `uv.lock` before
publishing.

## Local source development

Install from the current workspace, then start or recycle the plugin:

```sh
oll plugin install . --source
oll plugin restart __OLL_PLUGIN_NAME__
oll plugin call __OLL_PLUGIN_NAME__ echo -- one two
```

After an edit, run the tests and `oll plugin update __OLL_PLUGIN_NAME__`. oll
creates the installed generation's own virtual environment, so it cannot reuse
the development `.venv/` itself, but uv reuses its shared cache and the lockfile.
Updating does not replace a running process; restart the plugin to load the new
generation.

## Local release development

Do not archive `.venv/`: Python virtual environments record installation paths
and are not relocatable. Instead, use PEX to build a movable launcher at the
path expected by `oll.toml`:

```sh
mkdir -p build/oll-release/package/.venv/bin
uv export --locked --no-dev --no-emit-project --no-hashes \
  --format requirements.txt \
  --output-file build/oll-release/requirements.txt
uvx pex -r build/oll-release/requirements.txt . -c __OLL_PLUGIN_NAME__ \
  -o build/oll-release/package/.venv/bin/__OLL_PLUGIN_NAME__
cp oll.toml build/oll-release/package/oll.toml
tar -czf build/__OLL_PLUGIN_NAME__-dev-x86_64-unknown-linux-gnu.tar.gz \
  -C build/oll-release/package .
```

`uv export --locked` makes the PEX consume the production dependency versions
from `uv.lock`. `--no-hashes` is required because PEX also adds this local
project, which has no archive hash. The packaged
`.venv/bin/__OLL_PLUGIN_NAME__` is a standalone PEX file, not a copied virtual
environment. It still needs a compatible Python interpreter on the target
machine.

Create `oll-release.json` in the project root:

```json
{
  "format_version": 1,
  "plugin_id": "__OLL_PLUGIN_ID__",
  "default_release": "dev",
  "releases": {
    "dev": {
      "packages": [{
        "target": "x86_64-unknown-linux-gnu",
        "path": "build/__OLL_PLUGIN_NAME__-dev-x86_64-unknown-linux-gnu.tar.gz",
        "archive": "tar.gz"
      }]
    }
  }
}
```

Choose the canonical target matching the PEX dependencies, then test it:

```sh
oll plugin install . --release dev
oll plugin restart __OLL_PLUGIN_NAME__
```

## Development loop

Use editable installation and source mode for everyday work: edit, test,
update, restart, and call. Before publishing, test the PEX through release mode
to catch interpreter, dependency, and manifest mistakes. Do not invoke the
console script directly; oll supplies the private endpoint and lifecycle.

## Publish a release

Build a PEX on or for each supported target, then upload its archive. Replace
each local `path` with a remote `url` and add the exact `size_bytes` and
SHA-256 `sha256`. Commit both manifests and `uv.lock`, tag the release, and
verify the public install:

Linux packages use `tar.gz`; Darwin packages use `zip`. Keep each filename,
target, and `archive` value aligned.

```sh
oll plugin install <git-remote> --release <release-id>
oll plugin restart __OLL_PLUGIN_NAME__
```
